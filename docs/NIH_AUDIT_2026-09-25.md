Las 10,000 imagenes faltantes del HDF5 son un bloque continuo del CSV completo:
filas de datos 25,000 a 34,999 (numeracion desde 1, sin contar la cabecera).
No se conoce aun la causa de esa omision. Se creo una **copia nueva**, sin modificar
ninguno de los dos HDF5 originales. Se incorporaron 9,149 PNG de los ZIP locales y
851 PNG de un [espejo publico de investigacion](https://nih-chest-x-rays.s3.us-east-2.amazonaws.com/images_1024x1024/).
Ocho muestras de los ZIP coincidieron byte a byte con ese espejo. Esta comprobacion
no equivale a un checksum oficial para las 851 imagenes descargadas. Los PNG se
redimensionaron a 256x256 y se reparo el indice `image_names`, que en el HDF5
original solo tenia 34,999 entradas. Una segunda lectura independiente verifico
las **112,120** imagenes de la copia nueva: 0 claves ausentes o extra, 0 indices
inconsistentes, 0 formas incorrectas y 0 errores al leer pixeles. El reporte
local completo se guarda junto al nuevo HDF5 como `.audit.json`.

Las 21,152 imagenes no seleccionadas pertenecen a pacientes asignados a val
(10,563 imagenes) y test (10,589 imagenes);
train conserva todas las imagenes de sus pacientes. **Correccion de interpretacion:**
el script y la configuracion historicos guardados en este mismo ZIP seleccionan
deliberadamente una imagen por paciente para val/test. Por ello, estos CSV cumplen
el protocolo historico y no tienen fuga entre pacientes. El script mas reciente de
`cxr-research` adopta otro contrato (todas las imagenes de cada paciente). No se
deben mezclar los dos protocolos ni comparar sus metricas como si fueran iguales.

## Splits nuevos para futuros entrenamientos

Se generaron `train.csv`, `val.csv`, `test.csv` y `manifest.json` en un directorio
local nuevo `nih_splits_full_v1_20260925`. El algoritmo fue estratificacion
multietiqueta por **paciente** (semilla 42, `iterative-stratification` 0.1.9),
con todas las imagenes de cada paciente en un unico split.

Una comprobacion independiente confirmo 112,120 IDs unicos, 30,805 pacientes,
cero pacientes compartidos, cobertura exacta del HDF5 y coincidencia de paciente,
vista y etiquetas con el CSV original. Las 14 columnas binarias de clase y
`is_no_finding` tambien coinciden con `Finding Labels`. **Los checkpoints v1/v2
actuales no son elegibles para una prueba independiente sobre este split nuevo**:
fueron entrenados con el protocolo historico y su backbone proviene de pesos
preentrenados en NIH. Este split es para un entrenamiento futuro con procedencia
y evaluacion definidas desde el principio.

Los scripts reproducibles son `tools/recover_nih_hdf5.py` y
`tools/create_nih_splits.py`; sus dependencias estan en `tools/requirements.txt`.
Ambos aceptan rutas de entrada y salida por CLI (`--help`) y rechazan sobrescribir
resultados existentes. El HDF5, los CSV con IDs de paciente y los reportes locales
se guardan fuera de Git; solo se versionan scripts, pruebas y conteos agregados.

## Acciones antes de usar las metricas como evidencia de tesis

1. Conservar hashes, fuente y copia nueva; si se obtiene el origen oficial de las
   851 imagenes del espejo, comparar sus checksums o pixeles con este respaldo.
2. Conservar los splits historicos y las predicciones locales para auditar la
   evaluacion reproducida. Para el protocolo nuevo, reentrenar/evaluar sin
   reutilizar el AUC previo.
3. Recuperar commit, configuracion y logs de entrenamiento; cotejar hashes de
   datos/splits con los usados realmente. La coincidencia de checkpoints con el
   respaldo no basta para certificar esa relacion.
4. Recalcular AUC/AUPRC por clase, sensibilidad y especificidad con umbrales elegidos
   solo en validacion. Mantener prueba y validacion externa HNAL separadas.

El AUC macro `0.8045` esta **reproducido localmente en el test historico**, con
una diferencia numerica de `0.00000725`; no es rendimiento clinico validado.
